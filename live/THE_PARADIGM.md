# THE PARADIGM — how the Ontinuity team-of-seats system coheres (living document)

This is the top-level map. It sits above the rubric, the manuals, and the specs and says how they fit together and how the system stays coherent as it grows. READ THIS FIRST on any cold boot, then the role-specific doc. It is a LIVING document: it is re-derived whenever the system's shape changes, in the same commit as the change (currency discipline, below). If this doc and the live system disagree, that is a defect to fix, not a thing to work around.

## THE CORE MOVE — ground from the record, not from priors
Every seat (operator, control, workers) is a model that will, left alone, reason from its training priors / private context — what control has called "artificial imagination" — concretely: TRAINING-DATA priors (a model's general knowledge of how systems usually work) substituting for ONTINUITY-FACTS (how THIS system actually works, which lives only in the corpus, never in any model's weights). The load-bearing rule: use training data for CAPABILITY (code, reasoning, language); NEVER for Ontinuity-facts. Where priors and corpus disagree about this system, the corpus wins. Ambiguity is the front door for this substitution — a vague instruction forces the model to guess, and guessing reaches into priors; precise, semantically-tight instructions leave no gap for imagination to fill. Precision prevents; the gate only catches. That is the root failure of this project: a seat asserting a capability is absent, re-deciding settled design, or fabricating state, because it reasoned from memory instead of the record. The completion target is structural rather than promissory: every seat re-derives its operating reality from the corpus before acting, and the system verifies the claim. The live bootstrap mechanism is not yet authoritative because its canonical count is stale/caller-selectable, and close enforcement remains OPEN; manual orientation is therefore still required. Execution substrate affects enforceability, but API/engine migration is not itself proof of grounding.

## THE FOUR SEATS (see OPERATING_RUBRIC.md for full role rules)
- OPERATOR: direction, priorities, final authority + rollback. Should interact with the PLANNING seat only; should NOT have to route between worker conversations or nudge sleeping workers as routine. Routing is the system's job, not the operator's.
- CONTROL / PLANNING: the one seat the operator talks to. Owns planning, dispatch, and record currency. Its current environment may hold tokens + box hands, but that possession is not blanket landing authority: Control may author or independently review, and only the clean non-author signer lands the exact reviewed version. A participant in the gated chain, never the unchecked deployer.
- WORKERS: capable peer model instances that build + review each other. A clean reviewer signs and lands the exact peer-authored version through admitted block-scoped capabilities; an editing reviewer becomes author and resubmits. Per-block scope, ground-from-corpus, park-don't-fabricate at tool budget.
- (emergent) the chain itself: task -> build -> peer review -> sign-off -> deploy -> fold. No single judgment ships unchecked.

## THE OPERATOR-LOAD PROBLEM (real, but not the current 1.0 action)
Chat-window workers sleep between turns and require a platform/user nudge; the mailbox can expose idle-with-work but cannot create a new chat turn. API/engine workers can long-poll and wake as processes. Broad auto-spawn, self-hosted Control, and large worker populations are explicitly NOT required for 1.0 unless a release test promotes them. The current dependency order is B1 scoped identity followed by B3 fail-closed completion, not an auto-spawn build.

Model tiering remains a post-1.0 cost direction, not a certified current policy: use the strongest justified model where review judgment is load-bearing and test cheaper models for bounded drafting/polling work. The invariant is not a vendor or model tier; it is that all actors use the same gated, documented mailbox lifecycle and no exact bytes ship on one actor's unchecked judgment.

## SELF-HOSTING CONTROL (post-1.0 direction; structural boot remains a 1.0 requirement)
Routing Control through an API/engine substrate may eventually reduce private-context drift, but it is not the present build and is not assumed sufficient. The 1.0 work is narrower: make boot-from-corpus authoritative and identity-bound under B1, make completion fail closed under B3, and prove the release conditions. Revisit Control migration only after those guarantees work across the existing provider-neutral boundary.

## CURRENCY DISCIPLINE (what keeps a growing system coherent)
The manual, the rubric, the punch list work because they are updated WHEN THE THING CHANGES, IN THE SAME COMMIT. The paradigm gets the same discipline: when the system's shape changes (a role, the chain, the substrate, the tiering), THIS doc is updated in the same commit as the change. A drifted paradigm is the same defect class as a drifted manual allowlist — and the bootstrap gate's CHECK 6 should verify a seat can reproduce THIS paradigm's invariants, not just the manual's. Make "paradigm current" a gate item alongside "manual current."

## HONEST CEILINGS (carried up from the rubric; do not paper over)
- Chat seats sleep between turns; only an operator nudge wakes them. The shepherd detects idle-with-work and ALERTS; it cannot re-enter a chat window. Walk-away needs API/engine seats.
- Until per-identity keys are fully live, seat identity is self-asserted (trusted-not-authenticated); the shared diag key is the known soft spot.
- Grounding-from-record REDUCES but does not ELIMINATE model imagination; the gate (no unchecked judge) is what catches what slips through. Architecture over trust.
