## 3. THE ANSWER TO "HOW COULD A DESIGN SESSION USE THE ERL WITHOUT AN ADVERSARIAL SESSION?"
It reads it; it does not write it. The ERL is a committed corpus file per project/branch (erl_<slug>.txt, pushed by github_push_erl) and a box endpoint (GET /api/ledger, "used by Projenius LEDGER_QUERY and ORIENT"). Any seat can read_repo it today. WRITING the ERL happens in exactly one place — SYNTHESIZE after a session whose results faced the Challenger — and that is by design: ESTABLISHED means "survived challenge." A design session that wants project memory written for it IS a Mode B session: /agent/start with the objective, ORIENT reads the ERL in, the contract is authored, the cycle runs, DISTILL and SYNTHESIZE write Knowtext and the ERL out. The chat seat's own continuity is the corpus rituals (fold, punch list, record, handoff), now gated. There is no shortcut, and there should not be one.

## 4. THE INCONGRUENCE, NAMED
The V2 frame (record 2026-09-13d) says the design door is the chat window and verification is a gate the design session calls. The map says Mode B is a session. Both are right once the layers are named: the CHAT SEAT (control) drives Mode B; a matter's MEMORY (Knowtext + ERL) is produced by the sessions the seat starts; the seat's own memory is the corpus rituals. "Calling the verification gate" IS /agent/start with a load-bearing objective. The seat's rituals and the engine's contract-queue loop were built by the same hand to the same shape (STATE §4 "gate-and-contract"; CM §7 "discipline -> mechanism"), and they meet in agent_queue.md. What this week did was make the SEAT layer's rituals mechanical (L1-L5). What the seat still lacks is what the engine already has for a session: an authored, frozen contract with VERIFIABLE/JUDGED criteria checked deterministically at close. That, and nothing new, is L6.5.
